# End-to-End Auth (Sign Up & Log In) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make signup and login work end-to-end for GARAGE, MECHANIC, and SHOP roles so a user can register, get auto-logged-in, land on their real dashboard, log out, and log back in.

**Architecture:** Add three JWT-guarded `GET /{role}/profile/me` endpoints to the NestJS API that resolve the caller's entity by `userId`. On the Next.js side, add server-component index dashboards that read the session, call `/me`, and redirect to the existing `[id]` dashboard; auto-login after registration; add a logout control; remove two broken pages.

**Tech Stack:** NestJS + Prisma (API, `mtokaa-api`), Next.js 16 App Router + NextAuth v4 (frontend, `mtokaahero`), TypeScript, pnpm.

## Global Constraints

- API runs on port `8080` with global prefix `/api`. Frontend runs on `3000`. `NEXT_PUBLIC_API_URL=http://localhost:8080/api`.
- Two separate git repos: API at `/home/alphauser/Documents/github/mtokaahero/mtokaa-api`, frontend at `/home/alphauser/Documents/github/mtokaahero/mtokaahero`. Commit to each independently.
- No test framework is in use in either repo; do **not** introduce one. Each task's "test" is a build and/or a runtime smoke check with exact expected output.
- JWT payload is `{ id, email, role }`; `JwtAuthGuard` sets `req.user = payload`, so `req.user.id` is the User id.
- Role→dashboard segment map: `GARAGE → garage`, `MECHANIC → mechanics`, `SHOP → vendors`.
- Skip email/phone verification — no backend support exists.
- Session shape (from `next-auth.d.ts`): `session.user.{id, role, accessToken, firstName, ...}`.

## Task 5: Frontend — server helper to fetch `/me`

**Files:**
- Create: `mtokaahero/lib/api/profile.ts`

**Interfaces:**
- Consumes: `NEXT_PUBLIC_API_URL`.
- Produces: `getMyProfile(role: 'GARAGE'|'MECHANIC'|'SHOP', accessToken: string): Promise<{ id: string } & Record<string, unknown>>` — throws on non-2xx.

- [ ] **Step 1: Create the helper**

```typescript
const API_URL = process.env.NEXT_PUBLIC_API_URL ?? 'http://localhost:8080/api';

const ROLE_PATH: Record<'GARAGE' | 'MECHANIC' | 'SHOP', string> = {
    GARAGE: '/garage/profile/me',
    MECHANIC: '/mechanic/profile/me',
    SHOP: '/shop/profile/me',
};

export interface MyProfile {
    id: string;
    [key: string]: unknown;
}

export async function getMyProfile(
    role: 'GARAGE' | 'MECHANIC' | 'SHOP',
    accessToken: string,
): Promise<MyProfile> {
    const path = ROLE_PATH[role];
    const res = await fetch(`${API_URL}${path}`, {
        headers: { Authorization: `Bearer ${accessToken}` },
        cache: 'no-store',
    });
    if (!res.ok) {
        throw new Error(`Profile lookup failed (${res.status})`);
    }
    return (await res.json()) as MyProfile;
}
```

- [ ] **Step 1: Create the garage index page**

`app/dashboard/garage/page.tsx`:

```tsx
import { getServerSession } from 'next-auth';
import { redirect } from 'next/navigation';
import { authOptions } from '@/lib/config/authOptions';
import { getMyProfile } from '@/lib/api/profile';

export default async function GarageDashboardIndex() {
    const session = await getServerSession(authOptions);
    if (!session?.user?.accessToken) redirect('/auth/signin');

    try {
        const profile = await getMyProfile('GARAGE', session.user.accessToken);
        redirect(`/dashboard/garage/${profile.id}`);
    } catch {
        redirect('/auth/signin');
    }
}
```

> Note: Next.js `redirect()` throws internally; do not wrap the successful `redirect` in a try that swallows it. The pattern above is correct because the successful `redirect` is the last statement in `try` and its thrown control-flow signal propagates — the `catch` only runs if `getMyProfile` rejects first. Keep it exactly as written.

## Notes for the implementer

- The successful-path `redirect()` in the index dashboards intentionally lives inside the `try` block. `redirect()` works by throwing a special Next.js error; the surrounding `catch` re-catches only `getMyProfile` failures because the `redirect` is the final statement. Do not "fix" this by moving `redirect` outside the try — that would change control flow. (Next.js documents this pattern.)
- If `pnpm build` on the frontend fails due to the pre-existing `tsconfig.tsbuildinfo` cache, delete `.next` and rebuild.
- Backend `me` routes MUST be declared before `:id` in each controller, or NestJS will treat `me` as an id and hit the DB with a literal `"me"`.
